# Coordination

## Contract

Apply when dependencies, delegation, integration, a changed basis or resumption need coordination. Input: the assignment, current sources, authority, state and effects. Output: an agreed next action, a coherent plan where needed, or a concrete blocker. Reuse information in the request and existing records; no tracking template is required merely to begin.

## Execution

1. Establish the requested outcome in the user's terms and what would demonstrate completion. Analysis, a decision, an accepted change and verified operation are different possible outcomes, not a task taxonomy. Identify who owns unresolved intent and acceptance. The coordinator may accept technical results within delegated authority; do not require new user confirmation for every reversible edit.
2. Separate accepted requirements, observed implementation and hypotheses. Preserve enough continuity for the actual work. A bounded answer may need only its sources and conclusion. A connected product needs shared contracts and end-to-end deliveries; individual assignments refer to them.
3. Use existing project tools and records when sufficient. Select additional execution support for a real ownership, dependency, recovery or evidence need, or an applicable project requirement. One coordinator can assign work sequentially under an explicit organizational control. Do not describe that as atomic technical enforcement. The local controller provides transactional admission, revision/sequence checks, claims and events; its state names and schemas apply when it is selected. Another adapter claiming those guarantees must actually provide them. Keep one owner of execution state and link the source of product intent. Never switch mechanisms to evade a failed criterion, live owner, spent budget or unknown effect.
4. Before starting, check inputs, hard dependencies, budget, the owner of writes, and shared resources. Serialize writes in a shared environment. Permit parallel implementation when there is real isolation and an established integration process. A worktree does not isolate a shared database, secrets, or external APIs.
5. Give a subagent the task, revision, basis, goal, consumes/produces, read/write scope, external effects, shared resources, invariants, checks, acceptor, budget, further delegation limits, and return conditions. Do not transfer the entire history when relevant sources are sufficient. A module does not automatically create a separate agent.
6. Receive the artifact or diff, basis, checks, new dependencies, and effects. Reconcile the revision and current baseline. Resolve semantic conflicts and check affected interfaces after combining the work. A clean merge does not prove compatibility.
7. When a new fact appears, distinguish an execution error, a decision error, and an error in the intended outcome. Identify the owner and consumers; reissue affected assignments, mark inapplicable evidence, and preserve compatible work. A revision change does not reset resource expenditure.

When the [local workflow](runtime-workflow.md) is selected, use its worker/review contracts and durable admission before actual host dispatch; record the native host result. Its `clarifying`, `ready`, `running`, `proposed`, `accepted`, `blocked`, `paused` and `closed` states keep activity and evidence currency separate. A terminal revision is not resumed; new work gets a new revision. These are the adapter's representation of the method's state distinctions, not mandatory tool calls for every request.

Choose isolation that fits actual interference. Separate worktrees protect working copies from ordinary interference; they do not restrict a process with access to other worktrees. Claim generations fence controller calls. Never reuse a conflicting resource merely because a lease elapsed. With the prepared Git adapter, integrate identified commits in a separate worktree and check its current files, including relevant uncommitted changes. A project's existing integration procedure may supply the same needed protection; a single local edit need not create another worktree.

## Pause and recovery

Preserve the goal, plan, authorizations, changes, owners, processes, known/partial/unknown effects, checks, expenditure, and next permitted step. On resume, reconcile the live environment and verify that no previous competing writer remains active. A cancellation request is not proof of termination. Reuse an old result only after reconciliation; do not overwrite the user's changes with an old summary.

A blocker identifies the missing fact or decision, its owner, and the condition for clearing it. Prepare concrete options before asking a person. Continue independent authorized work. A no-op is valid when the plan and data are current. If a record is lost, reconstruct facts rather than inventing history.
